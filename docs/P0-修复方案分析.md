## 1. P0-1 trustSerialData 适配（#8）

### 背景

- JDK 8u191+：`com.sun.jndi.ldap.object.trustURLCodebase` 默认 false，BASIC 远程类加载链路在默认配置客户端失效（本地测试机 JDK 8u291 即受此约束）。
- JDK 8u381 / 11.0.20 / 17.0.8+ 起：`com.sun.jndi.ldap.object.trustSerialData` 默认 false，LDAP 条目里的 `javaSerializedData` 不再被客户端反序列化，gadget 链路整体失效。

### 现状

`LdapServer.sendResult`（`src/main/java/com/bloom/server/LdapServer.java:104-112`）：非 BASIC 分支一律走 `payload.choiceTypeByswitch(base)` 生成 base64 串，塞进 `javaSerializedData`。新 JDK 客户端全部拒绝。

### 机理：为什么 BeanFactory 系可以直返

EL / groovy / snakeyaml / XStream / mvel / BeanShell2 / JDBC 系链路的利用载体是 `javax.naming.Reference`（`ResourceRef`），客户端经 `NamingManager.getObjectInstance` → `BeanFactory.getObjectInstance` 强制转换 `forceString` 属性触发。这条路径：

1. 只读 LDAP 属性（`javaClassName`、`javaFactory`、`javaReferenceAddress`），不读 `javaSerializedData`，天然不受 `trustSerialData` 约束。
2. 不需要远程 codebase，天然不受 `trustURLCodebase` 约束。

### 方案

1. 新建 `com.bloom.exploit.RefFactory`：按 payloadType 构造 `Reference`，覆盖 13 类（EL、ELjakarta、groovyBytomcat、snakeyaml、XStream、mvel、BeanShell2、tomcat_dbcp1/2、commons_dbcp1/2、druidjdbc、tomcatjdbc）。构造逻辑从 `com.bloom.exploit.payload` 的 BeanFactory 系 case 中搬迁复用。
2. `LdapServer` 非 BASIC 分支默认改为直返：把 `Reference` 拆成 LDAP 属性写入条目，`javaReferenceAddress` 按 RefAddr 序号编码（`#0`、`#1`…，值为类型与内容的分隔表示，unboundid 侧可借助 `ReferenceHelper` 语义手写编码）。不再写 `javaSerializedData`。
3. 开关 `--force-serialize`：保留旧行为回退，用于对照实验。
4. `payload.java` 中对应 case 改为调用 `RefFactory`，消除两处构造逻辑并存。

### 验证标准

- 集成测试新增断言：BeanFactory 系路由返回条目含 `javaClassName` / `javaFactory` / `javaReferenceAddress`，不含 `javaSerializedData`。
- 加 `--force-serialize` 后行为回退（`javaSerializedData` 出现）。
- dry-run 路由解析不受影响。

## 2. P0-2 basic/memshell（#9）—— 实测修正

### 实测结果（本机回环，2026-08-04）

| 路由 | javaFactory | HTTP 状态 | 结论 |
|---|---|---|---|
| `basic/base64/aWQ=` | `Exploit<随机>` | 200 | 正常（`LdapServerIntegrationTest` 已覆盖） |
| `basic/memshell/TomcatFilterMemShellFromThread` | `ysoserial.payloads.templates.TomcatFilterMemShellFromThread` | 200 | 正常：`Cache` 静态块预缓存了 9 个类，HTTP 端 `handleClassRequest` 取 URL 文件名作 key，恰好命中 |
| `basic/memshell/FILE:Exploit` | `Exploit` | 200 | 正常：`data/Exploit.class` 磁盘兜底 |
| `basic/memshell/<任意未预缓存名>` | FQCN | **404** | 失效：路由解析报 `[OK]`，但类不存在，客户端 ClassNotFoundException，静默失败 |

原任务描述「javaFactory 类名与 HTTP serve 缓存 key 不一致导致 404」只对未预缓存类成立：FQCN 当中间路径存在时，HTTP 端取文件名的行为掩盖了 key 不一致；自定义类名（无包名）与 `FILE:` 分支才真正踩中错配。

### 真正断点（3 个）

1. `CommandTemplate` 的 `CLASS:` 分支（`CommandTemplate.java:22-32`）：字节码加载代码整段被注释，`bytes` 恒为 `null`，`cache()` 跳过写入。能否投递完全取决于 `Cache` 静态块是否预缓存了这个名字。
2. `CommandTemplate` 的 `FILE:` 分支（`CommandTemplate.java:33-42`）：同样被注释，依赖 `data/` 目录磁盘兜底。
3. `RouteParser` 不校验 memshell 名是否存在：`basic/memshell/不存在的东西` 在 dry-run 与日志里都显示合法，失败只发生在目标端，无法本地发现。

### 修复方案（≤50 行）

1. `CommandTemplate` `CLASS:` 分支：恢复 `generateMemshell(Class.forName(loadshell))`，`catch` 到 `ClassNotFoundException` 时明确报错并置失败态，不要静默继续。
2. key 统一为简单类名：`CLASS:` 分支的 `className` 存 `cmd.substring(6)`（不带包名），`Cache` 静态块、HTTP 端、javaFactory 三处自然对齐（HTTP 端本来就截文件名）。
3. `FILE:` 分支：恢复从 `data/` 读字节码（原注释代码可用），文件不存在同样明确报错。
4. 可选：在 `RouteParser` 对 memshell 名做白名单/存在性校验，dry-run 即可发现非法名。

### 验证标准

- 集成测试补充：`basic/memshell/TomcatFilterMemShellFromThread` → 200（回归），`basic/memshell/NoSuchShell` → 服务端明确报错而非 200 假象。
- dry-run 对非法 memshell 名输出校验失败。

## 3. P0-3 jakarta 双轨（#5）

### 现状与阻塞

- `pom.xml` 未引入 `jakarta.el:jakarta.el-api` / `org.glassfish:jakarta.el`，ELjakarta 链需要先加依赖。
- 本地仓库 `/Users/lvzhibo/.m2/repository/javax/interceptor/javax.interceptor-api/3.1/javax.interceptor-api-3.1.jar` 文件损坏（编译期 `error in opening zip file`，当前靠剔除该条目绕过）。引入 jakarta 依赖前先删除该目录让 Maven 重下，否则编译阶段 javac 会失败。

### 方案

1. `RefFactory`（#8 新建）增加 ELjakarta 分支：`jakarta.el.ELProcessor` 等价替换 `javax.el.ELProcessor`，其余构造同 EL 链。
2. 三个 FromThread 内存马模板复制为 jakarta 变体（`TomcatFilter/Listener/ServletMemShellFromThread`）：`javax.servlet` → `jakarta.servlet`，无逻辑差异。原范围确认过：只做 FromThread 三个变体。

### 验证标准

- dry-run 路由 `ELjakarta/...` 解析通过。
- 集成测试：ELjakarta 路由返回 Reference 直返属性（依赖 #8 完成后）。
- jakarta 变体模板能独立编译（`mvn compile` 通过，需 jakarta.servlet-api 依赖 scope=provided）。
